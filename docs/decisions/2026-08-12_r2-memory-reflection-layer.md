# R2 — 메모리 증류 reflection 레이어 (L4 강화)

**날짜**: 2026-08-12
**성격**: 설계 문서 — 미착수(로미 개선 브리프 §3 R2).
**관련 파일**: `src/lib/memory/service.ts`(`recordSignal`·`readBrain`), `src/lib/memory/distill.ts`(`updateBrainWithSignals`), `src/lib/ai/companion.ts`(`narrateVisit` — 유일한 기존 "회고 시점 LLM 한 겹" 전례), `src/lib/types/index.ts`(`UserBrain`)

## 배경 — 현재 L4는 순수 숫자다

`recordSignal`(`service.ts:27`)은 신호가 쌓일 때마다 **동기로** `updateBrainWithSignals`를 호출해 confidence를 재계산한다. 이건 이미 "결정론 증류"고 이미 잘 동작한다 — 문제가 아니다.

문제는 **브레인이 숫자(confidence)와 slug 라벨만 갖고 있다**는 것. "이 사람은 발견보다 굿즈에 강하게 반응한다"·"이 사람은 첫 전시에선 넓게 보다가 최근엔 좁혀서 본다" 같은, 클릭 카운트만으론 안 드러나는 **정성적 패턴**은 어디에도 안 남는다. 컴패니언이 재방문자를 "구체적으로" 알아보려면 이 층이 필요하다(브리프의 수용 기준: "재방문 시 로미가 지난 관람을 구체적으로 참조").

기존 전례: `narrateVisit`(`src/lib/ai/companion.ts:9`)이 회고 시점에 `VisitDigest` 하나를 LLM 한 번으로 서술형 문장으로 바꾼다 — **요청 안(reflect API 호출 중), 회고라는 명시적 사용자 액션 뒤**에서만 돈다. speed rule과 안 부딪히는 유일한 실제 사례라 이번 설계의 템플릿으로 쓴다.

## 목적

세션 사이(관람이 끝난 뒤, 다음 방문 전)에 raw 신호 원장을 재정독해 브레인에 **짧은 서술형 메모**를 추가한다. confidence 숫자를 대체하지 않고 보강한다.

## 설계 — 데이터 모델

`UserBrain`에 새 필드 추가:
```ts
reflectionNotes?: {
  text: string;        // "발견보다 굿즈 쪽에 반응이 뚜렷해" 같은 한 줄
  basedOnVisits: number; // 이 메모가 반영한 visits[] 길이 — 재생성 트리거 판단용
  updatedAt: string;
}[];
```
최대 3~5개 유지(오래된 건 밀려남 — "저장 아니라 증류" 원칙, 무한히 안 쌓는다).

## 설계 — 언제 도는가 (트리거 옵션 비교)

- **A. 회고(reflect) 시점에 얹기** — `narrateVisit`과 같은 호출 안에서 `reflectionNotes`도 같이 갱신. 새 인프라 불필요, 기존 1회 호출 지점 재사용.
  - 장점: 배관이 이미 있다(요청 안 LLM 호출 1회, 이미 승인된 패턴). 별도 배치/스케줄러 불필요.
  - 단점: "세션 사이"가 아니라 "이번 세션 끝날 때"다 — 브리프가 말한 "세션 사이 재정독"과는 살짝 다르다(그래도 실질적으로 같은 타이밍: 다음 방문 전에 갱신되면 됨).
- **B. 완전히 별도인 오프라인 배치**(cron/스크립트, 전체 사용자 순회) — 브리프 문구에 더 literal하게 맞는다.
  - 단점: 이 프로젝트엔 cron 인프라가 없다(scripts/는 운영자가 수동 실행). 새 배치 러너를 만들어야 하고, "언제 도나"(매일? 로그인 시?)를 새로 정해야 한다 — 결정할 게 늘어난다.
- **권장: A.** 브리프의 실제 요구("재방문 시 구체적으로 참조")를 만족시키는 데 필요한 건 "다음 방문 전 갱신"이지 "세션 사이 정확히"가 아니다. 이미 있는 회고 호출 지점에 필드 하나 얹는 게 새 배치 인프라를 만드는 것보다 훨씬 작은 변경이고, 실패 시 폴백도 `narrateVisit`과 같은 패턴(LLM 실패 → 이번 회차는 메모 안 남기고 넘어간다, 브레인은 여전히 유효)을 그대로 쓸 수 있다.

## 설계 — 프롬프트 입력

`reflectFromSignals`(`service.ts:198`, 회고 API가 호출하는 기존 함수) 안에서 `narrateVisit` 호출과 나란히:
- 입력: 이번 방문 `VisitDigest` + 직전 `reflectionNotes`(있으면, 누적 참고용) + 상위 confidence 관심 3~5개.
- 프롬프트 지시: "숫자를 나열하지 말고 패턴 하나만 한 문장으로. 확신 없으면(신호가 너무 적으면) 아무것도 쓰지 마라" — **없는 패턴을 지어내지 않는다**(grounding.ts의 빈말 금지 원칙과 동일 선상). 신호가 적은 사용자(방문 1회, 판단 2~3개)는 `reflectionNotes` 갱신을 스킵.

## 사용처 — 컴패니언 프롬프트 주입

CLAUDE.md 원칙("브레인은 항상 프롬프트에 주입되는 신원")대로, `reflectionNotes`는 다음 두 곳에 노출한다:
- 전시 홈 재방문 인사(`HomeCompanionContextBridge`가 이미 `interests`를 넘기는 자리에 `reflectionNotes` 최신 1개 추가).
- **주의**: 이건 발화 텍스트가 아니라 **판단 재료**로만 넘긴다 — 화면에 그대로 노출하면 "로미가 나를 프로파일링해서 보여준다"는 느낌이 될 수 있다. R3(카피라이팅 엔진)가 이걸 자연스러운 문장으로 녹이는 역할을 한다 — R2는 재료를 만들고 R3가 말로 바꾼다는 분업.

## 수용 기준

- 판단 5개 이상 쌓인 사용자가 회고를 마치면 `reflectionNotes`에 새 항목이 추가된다(신호 부족 시 스킵 — 억지로 안 만든다).
- LLM 실패 시 회고 자체(narrateVisit)는 정상 진행되고 `reflectionNotes`만 갱신 안 됨(부분 실패가 전체를 막지 않는다).
- `updateBrainWithSignals`(결정론 confidence 계산)는 이 레이어와 완전히 독립 — reflectionNotes가 없어도 추천 스코어링은 그대로 동작(신규 필드는 optional).

## 리스크 / 미해결

- 언어 일관성 — `reflectionNotes.text`는 로케일별로 따로 생성해야 하나, 아니면 ko로만 만들고 en 사용자에겐 숨기나. 이번 앱의 로케일 지원 범위(ko 우선, en 보조) 확인 필요 — 결정 안 함, 구현 시 판단.
- "패턴 하나"의 신뢰도 — LLM이 우연한 상관관계를 패턴으로 서술할 위험. 승인 없이 바로 프롬프트에 들어가므로, 최소한 "확신 없으면 쓰지 마라"는 지시를 프롬프트에 명시하고, 초기엔 내부 검증(실제로 재방문자에게 보여줬을 때 이상한 소리를 하는지) 기간을 두는 게 안전.
