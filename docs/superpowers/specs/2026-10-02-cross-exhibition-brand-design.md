# 행사를 넘는 브랜드 — 설계

2026-10-02. 사용자 요청: "이미 다른 행사에 나왔던 브랜드면 새로 찾지 말고 그 데이터를
가져와 쓰고, 오히려 업데이트하자. 로미가 '지난 마곡리빙마켓에서도 보였던 브랜드야'라고
말할 수 있어야 한다. 행사끼리의 연결성을 고려한 서비스여야 한다."

## 1. 문제

부스는 행사마다 따로 산다. 같은 브랜드가 두 번째 행사에 나와도 시스템은 처음 보는 것처럼
명단 → 링크 찾기 → 이미지 → 초안 → 검수를 처음부터 다시 돈다.

운영 실측(2026-10-02, 참가 부스 1,578곳 / 행사 5개):

| | |
|---|---|
| 이름·인스타·웹 도메인 중 하나가 2개 이상 행사에 걸친 키 | 29개 (브랜드 약 20곳) |
| 주류박람회 ↔ 마곡리빙마켓 겹침 | 메멜트·블리스(남아공 육포)·평산댁닭발·페렐로 올리브·헬레닉와인·더더치치즈앤모어 |
| 셋 이상 행사에 나온 브랜드 | 메멜트(하우스 아카이브·마곡리빙마켓·주류박람회), 블루토마토즈 |

주류박람회에서 이 6곳은 마곡리빙마켓 때 사람이 확인·승인한 소개와 사진이 이미 있었는데
다시 초안을 돌렸다. 행사가 늘수록 겹침은 늘고, 낭비도 같이 는다.

그리고 **로미가 말할 수 있는 게 하나 빠져 있다.** "이 브랜드는 전에도 봤다"는 건 방문객에게
실제 판단 근거다(검증된 곳, 다시 온 곳). 같은 사용자가 그때 반응했다면 더 강하다 —
`docs/decisions/2026-07-07_knowledge-architecture.md`의 L4(종단 사용자 기억)가 행사를 넘어
쓰이는 첫 자리다.

## 2. 목표 / 비목표

**목표**
1. 부스(이번 행사의 자리)와 브랜드(행사를 넘는 정체)를 나눈다.
2. 새 행사 인입 때 이미 아는 브랜드면 지난 정보를 **초안으로** 미리 채운다.
3. 새로 확인한 정보가 다음 행사로 이어진다(업데이트).
4. 로미가 브랜드의 지난 출전, 그리고 그 사용자의 지난 반응을 근거로 말한다.

**비목표**
- 브랜드 페이지를 방문객용 독립 화면으로 만들기 — 부스 상세 안의 한 섹션으로 충분하다.
- 회사(법인)와 브랜드의 계층. 한 회사가 여러 브랜드를 내는 경우(와인 수입사의 여러 라벨)는
  지금은 브랜드 하나로 본다.
- 이름 유사도만으로 자동 연결. 아래 §4에서 사람 확인으로 돌린다.

## 3. 개념과 데이터 — 0040을 그대로 쓴다

**이미 설계·적용돼 있었다.** `0040_exhibitor_history.sql`이 운영에 적용돼 있고 세 테이블 모두
0행이다(쓰는 코드가 없었다). 새 테이블을 만들지 않고 이 구조를 채운다.

```
exhibitor (참가사 마스터 — 행사를 넘는 정체)
  canonical_name · aliases · website_url · instagram_url
exhibition_participant (회차별 참가 사실)
  exhibition_id · exhibitor_id · display_name ← 그 행사에 표기된 명칭
booth_participant (물리 부스 ↔ 참가 사실, 다대다)
  booth_id · participant_id · role primary | co_exhibitor
user_exhibitor_judgment_history (뷰)
  사용자 판단(booth_note) → 참가사 → 다른 회차
```

- **이름은 행사에 표기된 명칭으로 보여준다**(사용자 결정 2026-10-02). `exhibitor.canonical_name`은
  운영자가 보는 내부 이름이고, 화면과 로미는 `exhibition_participant.display_name`을 쓴다.
  "지난 마곡리빙마켓에 '블리스'로 나왔던 브랜드야."
- **소개·사진은 참가사에 복사하지 않는다.** 참가사의 "현재 정보"는 연결된 부스들 중 가장 최근에
  승인된 저작을 읽어 낸다. 정보를 두 곳에 두면 어느 쪽이 진실인지 갈라진다. 그래서
  **업데이트는 따로 하는 일이 아니다** — 새 행사에서 고쳐 승인하면 그게 다음 원천이 된다.
- 공동입점(주류박람회 H-20 제이엘아이앤씨 + 언보틀드)은 `booth_participant`의 primary +
  co_exhibitor로 그대로 표현된다. 사용자 판단은 primary에만 귀속된다(0040의 규칙).
- 시설(kind = facility)은 참가사가 없다.
- 새로 필요한 것은 **연결 후보** 하나: `0057_exhibitor_link_candidate`
  (booth_id, exhibitor_id, reason, status pending|approved|rejected). RLS는 0040과 같다
  (읽기 공개, 쓰기 서비스 롤).

## 4. 연결 규칙 — 언제 같은 브랜드인가

| 근거 | 처리 | 이유 |
|---|---|---|
| 인스타 핸들이 같다 | **자동 연결** | 핸들은 고유하다 |
| 웹사이트 등록 도메인이 같다(플랫폼 제외) | **자동 연결** | 같은 회사 |
| 정규화한 이름만 같다(3자 이상) | **연결 후보 → 사람 확인** | 이름은 겹친다 |
| 이름이 비슷하다 | 아무것도 안 함 | 오탐이 확인 비용보다 크다 |

- 플랫폼 도메인(인스타그램·스마트스토어·네이버 블로그·linktree·카카오 등)은 도메인이 아니라
  **첫 경로(계정)**로 본다 — 품질 게이트의 신원 앵커(`anchorKey`, quality-gate.ts)와 같은 규칙을
  공유한다. 두 곳이 갈리면 "같은 브랜드"의 정의가 둘이 된다.
- 이름만 같은 경우를 자동으로 묶지 않는 근거: 2026-10-01 인스타 대조에서 "분주"의 검색 1순위가
  탄자니아 회사였다. 이름 일치는 신호지 증거가 아니다.
- 연결 후보는 `exhibitor_link_candidate`에 쌓고, 운영 콘솔 **대조 검수 쪽의 별도 화면**
  "같은 브랜드인가요?"에서 본다(사용자 결정 — 초안 검수와 섞지 않는다). 두 회차의 부스를
  나란히(이름·인스타·웹·소개·사진) 놓고 고른다. 승인하면 그 부스의 참가 사실을 기존 참가사에
  잇고, 반려하면 새 참가사로 둔다.

## 5. 인입에 끼우기

`planIntake`(순수)에 브랜드 목록을 넘긴다. 부스마다:

1. 같은 행사 안에 이미 그 code의 부스가 있으면 기존 규칙 그대로(빈 칸만 채운다).
2. 새 부스면 §4 규칙으로 브랜드를 찾는다.
   - 자동 연결 → 기존 참가사에 이번 회차 참가 사실(display_name = 이번 표기)을 만든다.
   - 이름만 일치 → 새 참가사로 두고 연결 후보를 남긴다(확인되면 합친다).
   - 못 찾음 → 새 참가사 + 참가 사실.
3. 연결된 참가사의 다른 회차 부스에 승인된 저작이 있으면 **이월 초안**을 만든다:
   `enrichment_candidate`에 `source: "carryover"`로, 원천 부스·행사를 출처로 단다.
   사진·로고·링크는 인입 파일에 없을 때만 원천 부스 값으로 채운다(빈 칸만 채우기 규칙 그대로).
4. 이월 초안은 **같은 승인 큐**를 탄다. 자동 통과 정책: 원천이 사람 승인이었고 연결이 자동
   (인스타·도메인)이었으면 자동 통과 후보. 이름 확인으로 연결된 건 사람이 본다.

행사마다 다른 것(timing·부스 이벤트·이번 행사 한정 굿즈)은 이월하지 않는다 — 지난 행사의
"선착순 50분 무료 티켓"을 이번 행사 사실처럼 말하면 거짓말이다. 이월 대상: summary·
roamInterpretation·valueTags·recommendationReasons·memoryHooks. thingsToDo는 브랜드 일반
행동만(행사 고유 표현이 들어 있으면 뺀다 — 게이트에 규칙 추가).

## 6. 로미가 말하는 것

근거 카드(`buildGrounding`, feed/grounding.ts)의 2절 재료에 하나를 더한다. 우선순위:

1. **내 지난 반응** — 이 브랜드의 다른 행사 부스에 내가 끌림·가봄을 눌렀다.
   "지난 마곡리빙마켓에서 네가 끌림 눌렀던 브랜드야."
2. 지금의 근거(기존) — 이번 행사에서 내가 누른 부스와 가치가 겹친다.
3. **브랜드의 지난 출전** — "지난 마곡리빙마켓에도 나왔던 브랜드야."

- 1은 0040의 `user_exhibitor_judgment_history` 뷰가 이미 조인해 둔다(booth_note의 interest·
  verdict → primary 참가사 → 다른 회차). 참가 사실만 채워지면 바로 읽힌다.
- 3은 사실이라 누구에게나 말해도 되지만, **피드당 횟수를 제한**한다(createLinkPicker의 maxUses와
  같은 방식). 모든 카드가 "지난번에도 나왔어"면 정보가 아니다.
- 1은 그 사용자에게만 보인다. 다른 사람의 반응은 말하지 않는다.
- 부정 반응(별로·패스)은 말하지 않는다 — "지난번에 별로라던 곳이야"는 판단을 대신 내려 버린다.
  피드 순위에만 반영(기존 브레인 경로).

부스 상세에는 "다른 행사에서도" 한 줄 섹션: 출전한 행사 이름, 그때 표기된 명칭, 부스 번호.

## 7. 백필

운영의 참가 부스 1,578곳 전부에 참가사·참가 사실·부스 배정을 만든다(스크립트 아님 — 관리자
라우트로, 인입과 같은 판정 함수를 쓴다). 0040 주석의 원칙("이름으로 자동 병합하지 않는다")을 지킨다.
- 인스타·도메인 일치 → 같은 참가사
- 이름만 일치 → 각자 참가사 + 연결 후보 큐
- 나머지 → 1부스 1참가사
- 공동입점(aliases)은 이번 단계에선 primary만. co_exhibitor는 별칭에 신원 근거가 없어 보류

예상: 자동 연결 수십 건, 후보 십여 건(위 실측 29키 기준). dry-run으로 숫자를 먼저 본다.

## 8. 단계

| 단계 | 내용 | 끝나면 |
|---|---|---|
| 1 | `0057_exhibitor_link_candidate` + 판정 함수(순수·테스트) + 백필 dry-run/적용 + "같은 브랜드인가요?" 화면 | 모든 부스가 참가사를 안다 |
| 2 | 인입에 브랜드 판정 + 이월 초안 | 다음 행사부터 아는 브랜드는 다시 안 찾는다 |
| 3 | 로미 2절 "지난 출전 / 내 지난 반응" + 부스 상세 섹션 | 행사 간 연결이 사용자에게 보인다 |

## 9. 검증

- 판정 함수: 단위 테스트(인스타·도메인·플랫폼 계정·이름만·짧은 이름).
- 저장소: mock 통과로 끝내지 않는다 — 운영 자격증명 로컬 서버로 백필 dry-run, 적용 후 재실행
  멱등(두 번째 실행에서 새 연결 0) 확인. `npm run smoke:prod`.
- 이월: 주류박람회 6곳을 실제 사례로 — 마곡리빙마켓 승인 저작이 초안으로 들어오는지,
  행사 고유 표현이 걸러지는지.

## 10. 결정 (2026-10-02)

1. 연결 확인은 **대조 검수 쪽 별도 화면** — 초안 검수와 섞지 않는다.
2. 이름은 **각 행사에 표기된 명칭** — `exhibition_participant.display_name`.
3. 새 `brand` 테이블 대신 **0040(exhibitor·exhibition_participant·booth_participant)**을 쓴다.
