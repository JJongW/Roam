# Roam — 운영 콘솔 · 자동화 아키텍처 설계

> 작성 2026-09-02. **특정 전시의 데이터 백로그는 다루지 않는다.** 지금 들어 있는 전시들은
> README가 선언한 대로 시드다. 이 문서가 설계하는 건 *어떤 전시가 들어와도 같은 비용으로
> 돌아가고, 전시를 거듭할수록 좋아지는 구조*다.

---

## 0. 설계 목표

**"새 박람회 하나가 Roam에 올라가서 지표가 나오기까지"를 예측 가능한 비용으로 만들고,
그 과정에서 쌓인 것이 다음 전시를 더 싸고 정확하게 만들도록 한다.**

README에 이미 선언되어 있다 — *"전시 추가는 코드 변경 없이 데이터로 가능하다."*
이 문서는 그 선언을 **부스 데이터 · enrichment · 사용자 학습 · 지표 · 운영**까지 확장한다.

### 성공 기준 (전부 전시 무관, 전부 추세 지표)

| 기준 | 목표 |
|---|---|
| 전시 온보딩 리드타임 (명단 확보 → 오픈) | ≤ 3일 |
| 부스당 사람 손 시간 | ≤ 30초, **하락 추세** |
| 자동승인률 | **상승 추세** |
| N회차 방문자의 추천 정확도 | **회차가 늘수록 상승** |
| 새 전시 추가 시 코드 변경 | 어댑터 1개 외 0 |

**절대값이 아니라 추세가 이 설계의 성패다.** 전시를 치를수록 손이 덜 가고 추천이 더 맞아야 구조가 작동하는 것이고, 매번 같으면 자동화가 아니라 도구를 하나 더 만든 것뿐이다.

## 1. 두 개의 누적 루프 — 이 설계의 뼈대

Roam에는 전시를 축으로 누적되는 학습 루프가 **두 개** 있고, 자주 혼동된다. 둘 다 admin에서 "나아지고 있는가"가 보여야 한다.

```
루프 A — 데이터 품질 학습 (운영자가 가르친다)
  초안 생성 → 승인/수정 → field_diffs 축적 → 다음 전시 초안이 더 좋아짐

루프 B — 사용자 취향 학습 (사용자가 가르친다)  ★ 로미
  온보딩 → 판단(꼭갈래/끌려/패스) → 결과(좋았어/그냥그랬어/아니었어)
       → UserSignal → UserBrain 증류 → 다음 전시 추천이 더 맞음
```

### 루프 B가 전시를 넘어야 하는 이유

로미는 **과거 전시와 앞으로의 전시 데이터를 축적해 사용자를 계속 학습하는 형태**다. 이게 단일 전시 앱과 Roam을 가르는 지점이고, 크로스 전시 기억(L4)은 "미구현 부채"가 아니라 **제품의 축**이다.

전시를 넘어 누적되면 생기는 것:

| 얻는 것 | 설명 |
|---|---|
| **콜드스타트 해소** | 처음 오는 전시에서도 이미 취향을 안다. 온보딩을 건너뛰거나 축약할 수 있다 |
| **취향 변화 추적** | "굿즈 중심이었는데 점점 발견 쪽으로" — 시간축이 생긴다 |
| **전시 추천** | "당신 취향이면 다음 달 이 전시" — 전시 밖에서도 Roam이 존재한다 |
| **부스 콜드스타트 해소** | 신규 전시의 부스도 유사 취향군의 반응으로 초기 점수를 얻는다 |

> **검증 지표**: `N회차 방문자의 추천 정확도`. 1회차 vs 2회차 vs 3회차를 비교했을 때
> 회차가 늘수록 정확도가 올라가야 로미가 실제로 학습하는 것이다. **이게 루프 B가
> 작동한다는 유일한 증거**이며 admin 전역 뷰의 최상단에 놓는다.


## 4. 인프라 — Kubernetes는 쓰지 않는다

**K8s는 지금 Roam에 순손실이다.** Docker는 쓰되 Compose까지만.

- **규모가 안 맞는다.** 서비스는 Vercel의 Next.js 하나, 나머지는 배치 잡이다. 부하는 전시 기간 며칠에 몰리고 그건 Vercel이 흡수한다.
- **운영 비용이 사람 시간이다.** 인증서·네트워크 정책·노드 업그레이드·etcd 백업. 떠안으면 Roam 본체가 멈춘다.
- **맥미니 위 k3s는 특히 손해다.** 배치 잡 돌리려고 컨트롤 플레인 + CNI + etcd를 얹는 셈. 장애 표면만 는다.
- **관리형은 최소 월 $70–150.** Gemini 호출에 쓰는 게 낫다.

| K8s에서 원한 것 | 진짜 필요한 것 | 해법 |
|---|---|---|
| 죽지 않고 계속 돌기 | 재시작 + 헬스체크 | Compose `restart: unless-stopped` |
| 기능별 격리 | 의존성·실패 격리 | 컨테이너 1개 = 워커 1개 |
| 어디서든 관리 | 원격 접근 | admin이 이미 Vercel에 있다 |
| 스케일 | — | 아직 필요 없다 |

```
┌─ Vercel ──────────────────────────┐   폰에서 항상 떠야 하는 것
│  Next.js + /admin + API + Cron    │
└──────────────┬────────────────────┘
        ┌──────▼───────┐
        │   Supabase   │  ← 진실의 원천. 잡 큐도 테이블로.
        └──────▲───────┘
┌──────────────┴────────────────────┐   하루 멈춰도 아무 일 없는 것
│  Mac mini — Docker Compose        │
│  worker × N                       │
└───────────────────────────────────┘
```

**원칙: 맥미니는 집 컴퓨터다.** 정전·재부팅·네트워크 끊김에 노출된다. **하루 멈춰도 사용자에게 아무 일 없는 것**만 올린다. 네가 폰으로 보는 것은 Vercel + Supabase에 있어야 어디서든 뜬다.

> **K8s가 맞아지는 시점**: 동시 전시 5개 이상 + 워커 오토스케일이 실제로 필요 + 인프라를 볼 사람이 따로 있을 때.

## 5. 전시 인입 — 어댑터가 확장성의 전부

주최 측마다 참가사 명단의 형태가 전부 다르다. **매번 파서를 새로 쓰면 자동화가 아니다.**

```ts
interface ExhibitionSource {
  id: string;
  fetch(): Promise<RawBooth[]>;
}

interface RawBooth {
  code: string;          // 부스 번호 — 자연키
  name: string;
  category?: string;
  officialUrl?: string;  // 브랜드 공식 웹
  socialUrl?: string;    // SNS (링크만 — 저장이 아니라 참조)
  description?: string;  // 주최 측 공식 소개문
  imageUrl?: string;     // 주최 측이 제공한 이미지
  hall?: string;
}
```

`exhibition-ingest`는 `RawBooth[]`만 받는다. 그 앞이 뭐든 상관없다.

| 어댑터 | 채우는 사람 | 깊이 | 비용 |
|---|---|---|---|
| **수기 입력 / admin 직접 편집** ★ | **우리** | 필요한 만큼 | 부스 수만큼 — 하지만 **아무에게도 의존하지 않는다** |
| CSV/엑셀 업로드 | 주최 측 | 얕음 (명단 수준) | 0 — admin에서 붙여넣기 |
| 참가사 셀프 폼 | 참가사(브랜드) | **깊음** (굿즈·이벤트·타이밍) | 0 — 폼 화면만 |
| 공식 API / HTML 파싱 | — | 얕음 | 전시당 반나절 |

★ **자체 입력이 기본값이고 나머지는 전부 보조다.** 외부에 의존하는 경로는 아무도 안 채워주면 그냥 멈춘다. `exhibition-ingest`가 `RawBooth[]`만 받도록 좁힌 이유가 이거다 — **우리가 손으로 넣든, 주최 측 CSV든, 참가사 폼이든 뒤쪽 파이프라인은 하나로 같다.**

### 세 입력구의 역할이 다르다

```
주최 측 CSV     → 한 번에 전부, 얕게    (부스번호·이름·카테고리·공식링크)
참가사 셀프 폼  → 부스마다 하나, 깊게  (굿즈·현장이벤트·타이밍 — 브랜드만 아는 것)
자체 입력·초안  → 언제나 가능           (위 둘이 비어도 서비스가 성립)
```

**세 경로 모두 같은 곳으로 들어간다 — `enrichment_candidate` → 승인 큐 → `upsertBoothEnrichment`.** 그래서 승인 큐(§7)가 먼저 서 있으면 새 입력구를 붙이는 건 화면 하나 값이고, 승인 큐가 없으면 입력구를 아무리 만들어도 들어온 데이터를 다룰 곳이 없다. **순서가 이걸로 결정된다.**

> **참가사 셀프 폼**은 Roam 자체 디자인(shadcn/ui + Tailwind v4 + Pretendard,
> `docs/brand.md`)으로 만든다. 인증은 계정 가입이 아니라 **부스 코드 + 초대 토큰** —
> 브랜드에 계정을 만들게 하면 그 자리에서 이탈한다. 제출은 곧바로
> `enrichment_candidate`(status `pending`)로 떨어져 기존 승인 큐를 그대로 탄다.
> 별도 파이프라인이 아니라 **같은 큐의 또 다른 입력구**다.

### 이미지도 여기서 풀린다

주최 측은 **이미 참가사에게서 이미지를 받아둔다.** 브로슈어·공식 사이트·안내 앱에 쓸 사진을 부스 배정 때 제출받기 때문이다. `RawBooth.imageUrl`은 명단에 딸려 오는 게 자연스럽다.

**브랜드 수백 곳이 아니라 주최 측 한 곳과 합의한다.** 협상 상대가 1/N로 줄고, 받은 이미지는 출처와 사용 권한이 명확하다. 못 받는 부스는 ① 브랜드 공식 웹 이미지 ② SNS 공식 임베드(URL만 저장) ③ 현장 촬영 ④ 텍스트만 — 근거 카드는 텍스트가 만든다.

## 6. 기능별 에이전트 (워커)

여섯 개. **LLM은 셋에만.** 나머지는 순수 코드 — "탭엔 LLM 금지, 피드 큐레이션도 결정론" 원칙의 연장이다.

| 워커 | 단계 | 하는 일 | LLM | 주기 |
|---|---|---|---|---|
| `exhibition-ingest` | ② | `RawBooth[]` → 정규화 → booth 생성 | ✗ | 온보딩 시 |
| `enrichment-drafter` | ③ | `generateGrounded`로 6종 필드 초안 + 출처 | ✓ | 큐 소진까지 |
| `quality-gate` | ④ | 스키마·중복·근거 검증 → 신뢰도 점수 | ✗ | drafter 직후 |
| `metrics-rollup` | ⑦ | 이벤트 → 일별·전시별·세그먼트별 집계 | ✗ | 매일 04:00 |
| `insight-writer` | ⑦ | 지표 → 자연어 브리핑 + 이상징후 | ✓ | 매일 1회 |
| `health-doctor` | 전역 | 실패 로그 트리아지 → 원인 + 패치 제안 | ✓ | 실패 시 |

### 판단 기준은 문서(skill)에 둔다

워커의 *실행 코드*는 결정론, *판단 기준*은 레포 문서에 두고 워커가 읽는다.

- `enrichment-drafter` → `docs/booth-enrichment.md` + `docs/brand.md`(로미 보이스)
- `quality-gate` → 검증 규칙 문서
- `health-doctor` → `CLAUDE.md`

규칙이 바뀌면 문서만 고치면 되고, 그 문서는 **사람도 읽는 같은 문서**다.

### 자가치유의 범위

| 워커가 스스로 | 사람에게 올림 |

| 소스 실패 시 대체 소스 | 새 전시 어댑터 작성 |
| 초안 재생성 · 잡 재큐잉 | 같은 작업 3회 연속 실패 / 비용 임계 초과 |

**`health-doctor`는 패치를 제안하고 PR을 올리지, 프로덕션에 자동 배포하지 않는다.** 승인 큐가 데이터의 게이트이듯 PR이 코드의 게이트다. 이 선이 없으면 "스스로 고치는 시스템"은 "스스로 망가지는 시스템"이 된다.

## 7. 승인 학습 루프 (루프 A)

```sql
create table enrichment_candidate (
  id            uuid primary key default gen_random_uuid(),
  booth_id      text not null,
  exhibition_id text not null,
  payload       jsonb not null,      -- 6종 필드 초안
  sources       jsonb not null,      -- generateGrounded가 준 출처 URL
  confidence    numeric not null,    -- quality-gate 점수 0..1
  status        text not null default 'pending',
  created_at    timestamptz default now()
);

create table approval_event (
  id           uuid primary key default gen_random_uuid(),
  candidate_id uuid not null references enrichment_candidate(id),
  actor        text not null,
  action       text not null,        -- approve | reject | edit
  field_diffs  jsonb,                -- ★ 뭘 어떻게 고쳤는지
  reason       text,
  created_at   timestamptz default now()
);
```

### `field_diffs`가 핵심

승인/반려만 기록하면 한 비트만 남는다. **무엇을 어떻게 고쳤는지**를 남기면 셋이 파생된다.

1. **필드별 정확도** — 어느 필드가 자주 틀리는지
2. **few-shot 자동 승격** — 자주 고쳐지는 패턴의 *수정 후* 버전을 다음 전시의 예시로
3. **필드별 자동승인 임계값** — 필드마다 따로 잡는다

> 첫 전시는 임계값 1.0(전부 사람)으로 시작해 통과율이 안정되면 내린다.
> **커버리지가 아니라 손 갈 일의 총량이 줄어드는 게 목표다.**
> 세 번째 전시가 첫 전시보다 싸지 않으면 설계가 실패한 것이고, 성공 기준의
> "하락 추세"로 즉시 드러난다.

## 8. 운영 콘솔 — 정보구조

### 지금 문제

admin이 `ADMIN_EXHIBITION_COOKIE` + `resolveAdminExhibition()`으로 **전시 하나를 골라야만 화면이 뜬다.** 전 화면이 단일 전시에 종속돼 있어서 "Roam 전체가 어떻게 되어가는가"를 볼 데가 없다. 루프 A도 루프 B도 전시를 넘어 누적되는데, 그걸 보여줄 자리가 없는 것이다.

### 3층 구조로 재편

```
L1  전역 대시보드 (전시 무관)          ← 기본 진입. 지금 없음
L2  전시별 대시보드                    ← 지금 admin이 하는 것 + 확장
L3  개체 상세 (부스 하나 / 사용자 하나)  ← 일부 있음
```

#### L1 — 전역 대시보드 (신규)

Roam이라는 서비스 전체의 상태. **전시를 고르지 않아도 뜬다.**

| 블록 | 내용 |
|---|---|
| **로미 학습 곡선** ★ | N회차 방문자별 추천 정확도. 회차가 늘수록 올라가야 한다 |
| 누적 사용자 | 총 사용자 · 활성 · **멀티 전시 방문 비율** |
| 취향 지형 | 전체 사용자의 가치 분포와 시간에 따른 이동 |
| 전시 포트폴리오 | 전시별 요약 카드 (기간 · 부스 수 · 방문자 · 정확도 · ROI) |
| 시스템 건강도 | 워커 상태 · 승인 대기 · 실패 건수 · 온보딩 리드타임 |
| 데이터 품질 추세 | 자동승인률 · 부스당 사람 손 시간 (루프 A 증거) |

#### L2 — 전시별 대시보드 (확장)

"이 전시에서 무슨 일이 일어났나"를 전부 답한다.

| 질문 | 지표 | 재료 |
|---|---|---|
| 몇 명이 서비스를 썼나 | 가입 · 로그인 · 활성 사용자 · 세션 | `User` · `VisitorSession` |
| 몇 명이 현장에 왔나 | 현장 활동 세션 (지도·부스 상호작용 발생) | `VisitorSession` · `AnalyticsEvent` |
| 어디를 많이 눌렀나 | UI 클릭 분포 · 화면별 체류 | `uiClickBreakdown` **(있음)** |
| 어느 부스를 많이 봤나 | 조회 랭킹 | `analyticsPopular` **(있음)** |
| **어느 부스 선호도가 높나** | 긍정반응률 = `좋았어` / 방문 | `UserSignal` |
| **어느 취향의 사람이 오나** | 취향 세그먼트 분포 | `onboardingValueBreakdown` **(있음)** + `UserBrain` |
| 어떻게 움직였나 | 히트맵 · 동선 흐름 · 퍼널 | `analytics{Heatmap,Flow,Conversion}` **(있음)** |
| 부스가 뭘 얻었나 | 부스별 ROI 퍼널 | 신규 집계 |

#### L3 — 개체 상세
부스 하나의 전체 지표 + 취향별 반응 / 사용자 하나의 여정 + 취향 변화 (`accounts/[id]` 확장)

## 9. 지표 — 특히 취향과 선호도

### 조회수 ≠ 선호도

`analyticsPopular`는 **많이 본 부스**만 안다. Roam은 판단 어휘가 예측(`꼭갈래`/`끌려`/`패스`)과 결과(`좋았어`/`그냥그랬어`/`아니었어`)로 분리돼 있어서 **좋아한 부스**를 정확히 잴 수 있다. 둘을 교차하면 네 사분면이 나온다.

| | 선호도 높음 | 선호도 낮음 |
|---|---|---|
| **조회 많음** | 간판 부스 — 주최 측 홍보 자산 | **기대 미달** — 소개문이 과장됐거나 enrichment가 틀렸다 |
| **조회 적음** | **숨은 보석** — 추천 가중치를 올릴 대상 | 관심 밖 |

우하단은 **enrichment 품질 문제**로 루프 A에 피드백되고, 좌하단은 **추천 로직 문제**로 루프 B에 피드백된다. 이 사분면 하나가 두 루프의 진단 도구가 된다.

### 취향 세그먼트 분석

온보딩 가치(`발견·체험·굿즈·소통·학습·트렌드·영감·가볍게`)와 부스 `value_tags`가 같은 축이라 그대로 교차할 수 있다.

- **방문자 취향 분포** — "이 전시는 굿즈·발견 성향이 60%"
- **취향 × 부스 선호 매트릭스** ★ — "굿즈 성향 방문객은 C존을, 학습 성향은 E존을 선호했다"
- **취향별 추천 정확도** — 어느 세그먼트에서 로미가 못 맞추는지 → 제품 개선 방향
- **전시 간 취향 이동** — 같은 사용자의 취향이 전시를 거치며 어떻게 변하는지 (루프 B 증거)

★ 이 매트릭스는 **주최 측에 파는 인사이트**다. "당신 전시엔 이런 취향의 사람이 오고, 그들은 이런 부스를 좋아했다"는 다음 전시 기획에 직접 쓰이는 정보이고, Roam이 단순 안내 앱이 아닌 이유다.

### 부스별 ROI

```
부스 [코드] · [브랜드]
  피드 노출     1,240
  상세 진입       310   (25.0%)
  실제 방문        88   ( 7.1%)
  긍정 반응        61   (69.3% of 방문)
  주요 방문 취향   굿즈 42% · 발견 31%
```

통계가 아니라 **주최자와 부스에 파는 자료**다. B2B 계약과 과금의 근거이고, 다음 전시 주최 측을 설득하는 물증이다. **전시 종료 시 자동 생성되는 리포트**로 만들면 전시가 끝날 때마다 세일즈 자산이 하나씩 쌓인다 (생애주기 ⑧).

### 집계 레이어가 전제 조건

`analytics/page.tsx`가 `_allAnalytics!()`로 전체 이벤트를 받아 클라이언트에서 집계한다. 언더스코어가 임시임을 말한다. 위 지표들은 전부 사전 집계 없이는 불가능하고, **폰에서는 데스크탑보다 먼저 죽는다.** `metrics-rollup`이 야간에 일별·전시별·세그먼트별 집계를 만들고 admin은 그걸 읽어야 한다.

## 10. 모바일

반응형이 아니라 **작업 분리**가 핵심이다.

| 폰에서 | 데스크탑에서 |
|---|---|
| 승인 큐 훑기 | 전시 온보딩 (CSV 업로드·매핑) |
| L1 전역 대시보드 확인 · 일일 브리핑 | 부스 대량 편집 |
| 알림 대응 | 스키마 · 마이그레이션 · 심층 분석 |

**승인 큐는 폰에 최적화된 작업이다.** 카드 하나 = 부스 하나, 좌우 스와이프로 승인/반려, 탭하면 편집. 이동 중에 수백 건을 처리할 수 있고, 이게 루프 A의 연료를 만든다.

```
승인이 쉬워짐 → 학습 데이터가 빨리 쌓임 → 자동승인 임계값이 내려감 → 승인할 게 줄어듦
```

- **PWA 설치** — 홈 화면에 앱처럼. 별도 앱 개발 불필요.
- **푸시** — FCM 키 자리가 `.env.example`에 있고 미설정. 이상징후·워커 실패용으로 켠다.
- **모바일 진입 화면** — 숫자 넷: `로미 정확도` · `승인 대기` · `진행 중 전시` · `실패 건수`.

## 11. 롤아웃

각 단계가 끝나면 **그 자체로 쓸 수 있는 상태**가 되게 쪼갰다.

> **진행 상태 (2026-09-06 갱신).** 실제 순서는 문서와 달라졌다 — Phase 4(인입)를
> Phase 2(승인 큐)보다 **먼저** 했다. 문서는 "승인 큐가 없으면 입력구를 만들어도
> 다룰 곳이 없다"고 했지만, `booth_enrichment` + `upsertBoothEnrichment`가 이미
> 그릇이었기 때문에 입력구부터 세워도 성립했다. 대신 **검수 없이 바로 반영**되는
> 상태이고, 그게 지금 남은 공백이다.

### Phase 0 — 계측 보강 + 집계 기반 + L1 전역 대시보드 (2주)
- ✅ **`analytics_event.user_id` 추가** — 0042(2026-09-04)
- ✅ 계측 규격서 — `docs/telemetry-spec.md`
- ⬜ `metrics-rollup` + 일별·전시별·세그먼트별 집계 테이블
- ⬜ `_allAnalytics` 의존 제거 — 지금은 `limit 2000` 캡이 걸려 있어 급하지 않다
- ✅ **L1 전역 대시보드** — `/admin`(2026-09-06)
- **끝나면**: 폰에서 Roam 전체 상태가 한 화면에 뜨고, 취향 × 행동 교차가 가능해진다

### Phase 1 — L2 지표 확충 (2주)
- 선호도 지표 (조회 × 선호 사분면)
- 취향 세그먼트 분포 + 취향 × 부스 매트릭스
- 부스별 ROI 퍼널
- **끝나면**: 지금 못 뽑던 질문들에 답이 나온다

### Phase 2 — 저장 구조 + 승인 큐 (1–2주) ★ 자체 파이프라인의 심장
- ⬜ `enrichment_candidate` + `approval_event` 스키마 ← **지금 여기가 남은 공백**
- ⬜ 모바일 우선 승인 큐 화면
- ✅ **admin 직접 입력·편집 경로** — `booth-manager` → `PATCH /api/booths/[id]`(이미 있었다)
- ✅ 반영은 기존 `upsertBoothEnrichment` 재사용
- **끝나면**: 데이터가 어디서 오든 받아서 검수·반영할 그릇이 선다. 루프 A 시작

### Phase 3 — 자동 초안 (2주)
- `enrichment-drafter` (`generateGrounded`) + `quality-gate`
- 한 존(10–15부스) 파일럿 → 품질 확인 후 확대
- Docker Compose 도입 (워커가 둘 이상 되는 시점)
- **끝나면**: 부스당 사람 손이 실제로 떨어진다

### Phase 4 — 내부 전시 인입 (1–2주) ✅ **완료 (2026-09-06, 순서를 당겨서 함)**
- ✅ 정규형 계약 `intake.v1` + 순수 계획 계산기 + `/admin/intake` 업로드 화면
- ✅ 부스·홀·분야 생성까지. 빈 칸만 채우고 충돌은 사람이 확인해야 덮인다
- ✅ 덤: venue/layout 분리 — 벽·입출구·화장실은 장소의 속성이라 홀마다 한 번만 저작
- ⬜ CSV 어댑터는 실제 주최 측 파일이 올 때 (`RawBooth[]` 정규형은 이미 이 모양)
- **끝났다**: 새 전시의 부스 골격을 파일 하나로 올린다. 운영에서 검증됨

### Phase 5 — 크로스 전시 기억 + 자가치유 (2–3주)
- L4 구현 — `UserBrain`이 전시를 넘어 누적
- N회차 정확도 지표 가동 (루프 B 증거)
- `insight-writer` 일일 브리핑 + 푸시
- `health-doctor` + PR 제안 흐름
- **끝나면**: 로미가 전시를 거듭하며 똑똑해지고, 그게 지표로 보인다

### Phase 6 — 외부 인테이크 (1–2주) — **가장 마지막**
- **참가사 셀프 폼 먼저** — Roam 자체 디자인, 부스 코드 + 초대 토큰 인증
  (명세: `docs/exhibition-intake-template.md`)
- 제출 → `enrichment_candidate` (`source: 'exhibitor'`) → 기존 승인 큐
- 주최 측 일괄 CSV는 **관계가 생긴 뒤에.** 참가사보다 정치적 비용이 크다

> **참가사가 주최 측보다 먼저인 이유**: 브랜드는 자기 부스 노출을 원하니 이해가 맞고,
> 협상 단위가 작아 하나가 거절해도 나머지가 돈다. 그리고 **이미지 권리자 본인이라
> 사용 동의가 깨끗하다** — 주최 측 경유는 "주최 측이 참가사 동의를 받아뒀다"는
> 전제가 필요한데, 직접 받으면 그 전제 자체가 사라진다.

> **왜 마지막인가**: 외부 입력은 *있으면 싸지는* 경로지 *없으면 멈추는* 경로가 아니어야 한다.
> Phase 2–4로 자체 파이프라인이 완성돼 있으면 폼은 **화면 하나 값**이고, 아무도 안 채워도
> 서비스는 그대로 돈다. 순서를 뒤집으면 남이 채워주기를 기다리는 구조가 된다.

> **검증 지점**: Phase 4까지 마친 뒤 신규 전시를 통째로 태운다. 그때의 `온보딩 리드타임`과
> `부스당 사람 손 시간`이 루프 A의 성적표다. 루프 B의 성적표는 그 다음 전시에 나온다 —
> 같은 사용자가 두 번째 전시에서 더 정확한 추천을 받는가.

| 엔드포인트 | 키 | 어휘 | 성격 |
|---|---|---|---|
| `POST /api/analytics/events` | `session_id` | `AnalyticsType` 7종 — `view` `dwell` `route_start` `route_complete` `booth_arrive` `event_bookmark` `ui_click` | 익명 계측 (fire-and-forget, 202) |
| `POST /api/me/signal` | **`user_id`** | `SignalKind` 9종 — `reaction_must/curious/pass`(관람 전) · `verdict_good/ok/bad`(현장) · `feed_click` `booth_bookmarked` `search_query` | 로미 학습 원장 (로그인 필수) |

둘 다 Zod로 규격이 고정돼 있고(`analyticsEventInputSchema`, `signalSchema`), iOS는 `/api/auth/{apple,google}/native`로 로그인한 뒤 **같은 두 엔드포인트를 호출하면 된다. 새로 만들 API는 없다.**

> **실제 위험은 "iOS가 다른 걸 쏘는 것"이다.** 자체 이벤트 이름을 쓰거나 `/api/me/signal`을 아예 안 부르면 지표가 반쪽이 된다. 두 enum을 **계측 규격서**로 뽑아 웹·iOS가 같은 문서를 보게 한다. 어휘 추가는 `src/lib/types/index.ts`의 enum 변경으로만 — 그게 단일 진실이다.

### ② 루프 B는 끊기지 않는다 — 진짜 공백은 `analytics_event.user_id`

`UserSignal`은 **이미 `userId` 기준**이다. `recordSignal(user.id, …)`이고 타입 주석에도 `userId = app_user.id`라고 명시돼 있다. 즉 **로미의 학습 원장은 처음부터 계정에 묶여 있고, 전시를 넘어 누적된다.** README의 P1(리뷰·커뮤니티가 `visitor_session.id` 기준)은 실재하는 이슈지만 루프 B를 막지 않는다 — 별건으로 낮은 우선순위에 둔다.

막혀 있는 건 다른 지점이다.

```
UserSignal      → user_id  ✅  (취향·판단·결과)
analytics_event → session_id 만 ❌  (클릭·체류·히트맵·동선)
                              ↑ 둘을 이을 키가 없다
```

그래서 **"어느 취향의 사람이 어디를 눌렀나"가 지금 구조로는 불가능하다.** 요구한 지표 중 가장 값어치 있는 교차가 정확히 여기서 막힌다.

**해법은 작다.** `analytics_event`에 `user_id` nullable 컬럼을 추가하고, `recordAnalytics`가 `getUserId()`를 함께 적으면 끝이다. 방문객 앱 전체가 로그인 게이트 뒤에 있으므로(`src/proxy.ts` — `roam_user` 쿠키 없으면 307) **실제로는 거의 모든 이벤트에 user가 있다. 지금은 그냥 안 적고 있을 뿐이다.**

> 마이그레이션 1개 + `recordAnalytics` 시그니처 한 줄. 비용 대비 효과가 압도적이므로 **Phase 0에 넣는다.** 늦게 넣을수록 소급 불가능한 데이터가 쌓인다.

### ③ "방문자" 3분류 — 코드에 근거가 이미 있다

`booth_arrive`(AnalyticsType)와 `verdict_*`(SignalKind, 주석에 *"현장, 몸으로 확인한"*)는 **현장에 있어야만 발생한다.** GPS·비콘 없이도 이걸로 나눈다.

| 분류 | 정의 |
|---|---|
| **서비스 사용자** | 해당 전시에서 이벤트를 하나라도 남긴 고유 user |
| **현장 방문자** | `booth_arrive` 또는 `verdict_*`를 하나라도 남긴 user |
| **원격 탐색자** | 이벤트는 있으나 위 둘이 없는 user (현장에 오기 전/오지 않고 피드만 본 사람) |

`reaction_*`(관람 전)과 `verdict_*`(현장)이 이미 분리 설계된 덕에 추가 계측 없이 성립한다. **원격 탐색자 → 현장 방문자 전환율**은 그 자체로 마케팅 지표가 된다.

> ROI 리포트에는 이 수치가 **Roam 기준 집계**임을 명시하고, 주최 측 실입장 집계와 나란히 둔다. 대체가 아니라 병기다 — 그래야 "Roam을 쓴 관람객 중"이라는 단서가 살고 숫자의 신뢰가 선다.

### ④ 주최 측 인테이크 템플릿 — `docs/exhibition-intake-template.md`

`RawBooth` 스키마를 그대로 편 CSV 양식 + 이미지 사용 범위 합의 항목. 별도 문서로 작성해 두었다. 주최 측에 이 파일 하나만 보내면 어댑터 없이 전시가 올라간다.

## 부록 — 이 설계가 지키는 것

- **두 루프가 모두 보여야 한다.** 데이터 품질(A)과 사용자 학습(B). 둘 다 전시를 넘어 누적되고, 둘 다 admin에서 추세로 확인된다.
- **LLM은 판단 노드에만.** 수집·저장·집계는 결정론.
- **사람은 승인만.** 생성·검증·반영은 자동, 판단은 사람.
- **게이트는 둘.** 데이터는 승인 큐, 코드는 PR.
- **집 컴퓨터에는 멈춰도 되는 것만.** 사용자와 관리자가 보는 것은 클라우드에.
- **규칙은 문서에, 실행은 코드에.**
- **전시별 특수 처리는 어댑터 안에만.** 그 바깥은 모든 전시가 같은 코드로 돈다.
