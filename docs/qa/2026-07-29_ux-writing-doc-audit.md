## P0 — 홈이 근거 없는 추천을 주장한다

**위치:** `src/app/(visitor)/page.tsx:91-107` · `src/lib/i18n/dictionaries.ts:180`

첫 번째 전시에 "로미 추천" 뱃지를 달고 이 문장을 출력한다:

> **네가 고른 관람 성향을 기준으로 먼저 보여줄게.**

그런데 그 순서는 취향과 아무 관계가 없다:

| | 정렬 기준 |
|---|---|
| 운영(Supabase) | `order("id", ascending)` — `supabase/repository.ts:477` |
| mock | 배열 삽입 순서 — `mock/repository.ts:91` |

`HomePage`는 `listExhibitions`와 `getCurrentUser`만 호출하고 **`getUserBrain`을 부르지
않는다.** 개인화 데이터가 스코프에 아예 없다. 코드 주석도 스스로 인정한다 —
*"추후 가치 매칭으로 고도화"*. 그러면서 바로 아래 주석은 *"데이터 지어내지 않음"*이라고
적혀 있다. **지어내고 있다.**

문서가 가장 강하게 금지하는 항목이다:

> §51-57 Romi should not: **Pretend to know emotions or private intent without evidence.**
> §797-812 로미가 나를 안다고 주장하는 게 아니라, 내가 한 선택을 근거로 지금의 제안을
> 설명하고 있다.

**지금 당장 드러난다.** `0027` 마이그레이션을 적용하면 `exh_house_archive_2026`이 id
정렬상 맨 앞이라, **8/13 개막 전시가 내일(7/30) 개막하는 SIF를 제치고** "네 취향
기준"이라는 문장과 함께 올라간다. admin 부스·이벤트·분석 3개 화면도 `limit: 1`로
`exhibitions[0]`을 쓰므로 빈 대시보드로 바뀐다.

**재료는 이미 다 있다.** `getUserBrain(userId)`(`repositories/types.ts:147`)이
`interests`(가치 slug별 가중치)·`literacy`·`preferences`를 주고, 부스마다 `valueTags`가
있다. `rankForExhibition`이 부스 단위로 하는 계산을 전시 단위로 집계하면 된다.

**선택지 (택1):**
- **A. 진짜 개인화** — 브레인 상위 가치 ∩ 전시 부스 `valueTags`로 전시를 정렬하고,
  근거 문장을 실제 겹친 가치로 채운다. 문서가 원하는 모습.
- **B. 정직한 축소** — 개인화를 구현할 때까지 "로미 추천" 뱃지와 근거 문장을 **뺀다**.
  정렬은 `start_date`로 바꿔 "곧 열리는 순"이라고 솔직히 말한다. 한 줄짜리 수정이고
  거짓 주장이 사라진다.

B는 오늘 할 수 있고 A는 설계가 필요하다. 둘 다 지금보다 낫다.

## P2 — 반응 피드백 (2026-07-29 정정: 구현돼 있음, 지도에서만 안 보임)

**문서 §463-511:** 끌림 / 나중에 / 별로 / 이미 봄 각각에 로미가 응답해야 한다.

**최초 감사는 틀렸다.** `toast`만 검색해서 "0건"이라 적었는데, 실제로는
`reaction-bar.tsx:57-78`의 `reactionLine()` + `say()`로 **이미 완전히 구현돼 있다.**
문구도 국문·영문 모두 있다(`dictionaries.ts:415-420`):
`오 {value} 좋아하는구나? 비슷한 거 더 챙길게.` / `킵해뒀어. 잊지 않게 챙겨둘게.` /
`{value}는 별로였구나 — 덜 보여줄게.` / `이미 봤구나. 다음 걸로 넘어가자.`

**진짜 문제는 표시 경로다.** `say()`는 컴패니언 스토어의 `flash`를 세팅하고
`companion-bar.tsx:59`가 그걸 렌더하는데, **`companion-bar.tsx:65`가 지도에서는
컴포넌트 자체를 숨긴다**(`if (pathname.endsWith("/map")) return null`).
지도의 부스 시트에도 `ReactionBar`가 있으므로, **지도에서 반응하면 문구가 생성되지만
띄울 곳이 없다.** 사용자가 "지도에서 별로 눌러도 차이가 없다"고 한 것이 이것이다.

## 백로그 (2026-07-29 사용자 지적, 사실 확인 완료)

1. **부스 소개에 존댓말이 섞인다** — 로미는 반말인데 소개 809개 중 **103개(13%)**가
   `~입니다`/`~해요`. 다만 이건 **작가 본인이 쓴 글**이라, 반말로 고칠지(로미 목소리로
   흡수) 인용으로 표시할지(출처를 밝힘)는 설계 판단이 필요하다.
2. **부스 상세의 로미 소개가 거의 같다** — `longDescription`이 순수 템플릿
   (`${name}의 부스입니다. 부스 번호 ${code}...`)이라 914개가 사실상 동일. `grounding.ts`는
   이미 summary 조각으로 차별화를 시도하지만, summary 없는 부스는 폴백으로 수렴한다.
   이제 테마 대분류·소분류·굿즈가 생겼으니 부스마다 다른 문장을 만들 재료가 있다.
3. **UI 위계 개선** — frontend-design 스킬로 별도 검토.
4. **전체 flow 개선** — 범위가 커서 별도 브레인스토밍 필요.
5. **관람 종료 후 flow** — "없음"이 아니라 **부실함**. `src/app/api/me/reflect/route.ts`
   (23줄)와 `src/components/companion/finish-visit.tsx`가 이미 있다. 요구된 건
   "취향 되묻기 → 다음 전시를 위한 질문 → 마무리 멘트"로, 지금 구현은 그 깊이가 없다.
   L4 종단 기억(knowledge-architecture)과 직결되므로 설계부터 필요.

## UI 위계 감사 (2026-07-29)

⚠️ **한계 먼저**: 브라우저 확장이 localhost에 접근하지 못해 **실제 화면을 보지 못했다.**
아래는 코드에서 확인 가능한 **구조적 위계**(제목 레벨·타입 스케일·시각 가중치 분포)
감사이고, 색·여백·리듬 같은 시각 판단은 포함하지 않는다.

### 고친 것

1. **피드 카드의 주인공이 서 있지 않았다.** 부스 이름이 섹션 제목과 완전히 같은
   `text-base font-bold`였고, 화자 라벨 "로미"가 `text-sm font-bold`로 거의 동급이었다.
   카드를 봤을 때 무엇이 주인공인지 크기로 드러나지 않는다.
   → 부스 이름 `text-[17px] font-extrabold`, 로미 라벨 `text-xs font-semibold muted`.
   위계: 부스 이름 17 > 섹션 제목 16 > 로미 발화 14 > 라벨·근거 12.
2. **한 페이지에 `<h1>`이 둘.** 전시 페이지의 전시명과 `value-onboarding.tsx`의 제목이
   모두 h1이라 문서 개요가 깨졌다 → 온보딩을 h2로(시각 크기는 유지).
3. **홈에 `<h1>`이 없고 `<h3>`가 h2 없이 나왔다** → 히어로를 h1으로, 목록 제목을 h2로.

### 확인했으나 문제 아니었던 것

- 부스 상세의 본문 크기 3종(16/15/14px)을 처음엔 "임의값 혼재"로 봤으나, 실제로는
  **16=섹션 제목 / 15=읽기용 산문 / 14=메타·라벨**로 일관된 3단 체계였다. 건드리지 않았다.

### 남은 것 (시각 확인 필요)

색·여백·리듬·모션은 화면을 봐야 판단할 수 있다. 브라우저로 localhost에 접근할 수
있게 되거나 스크린샷을 받으면 그때 이어서 본다.
