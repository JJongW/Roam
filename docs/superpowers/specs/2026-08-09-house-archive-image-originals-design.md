# 하우스 아카이브 부스 이미지 원본 보존 설계

## 배경 — 무슨 일이 있었나

2026-07-29 이후 세션에서 하우스 아카이브 H존·T존(31개 부스)+M03 콜라보 텍스트를
반영하는 작업(0032·0033 마이그레이션, `enrichment-house-archive-2026.json` 확장)을
진행하는 동안, 이번 작업 범위와 무관한 기존 부스 3곳(C02·C14·G14)의 대표 이미지가
조용히 바뀌어 있었다. 원래는 브랜드 고유 사진이었는데, 행사 공용 홍보 전단으로
바뀐 상태였다 — `gen-house-archive-enrichment.mjs`가 갱신된 원본 소스 디렉터리
(`public/house_archive_br/house_archive_images/`, gitignore 대상)를 대상으로
재실행되면서, 해당 브랜드의 인스타그램 계정에 "최신" 스크린샷으로 잡힌 게 마침
행사 공식 전단 리포스트였고, 그걸 그대로 크롭해 덮어썼기 때문으로 추정된다.

이 사고가 배포 전에 걸러지지 않은 근본 원인: **크롭에 쓰인 원본이 로컬에만
(gitignore로) 존재해서, git diff에 "원본이 왜 바뀌었는지"가 전혀 안 보인다.**
결과물(webp)만 바뀐 채 커밋되면 리뷰어가 알아챌 방법이 없다.

세 부스는 이번 스펙 작업 중 `git checkout HEAD --`로 원복했다(별개 처리, 완료).

## 목표

- 크롭에 쓰인 원본 이미지가 로컬 폴더 유실/오염과 무관하게 항상 복구 가능해야 한다.
- 사이트에 실제로 노출되는 파생 이미지(webp)는 지금처럼 빠르고 저렴하게 서빙되어야
  한다.
- 제3자(브랜드·사진작가) 소유의 원본 콘텐츠가 의도치 않게 public 레포로 재배포되지
  않아야 한다.
- 비용·새 의존성 추가는 실제 규모에 맞게만 — 지금 있는 것으로 되면 그걸 쓴다.

## 비-목표 (일부러 안 하는 것)

브레인스토밍 중 검토했지만 이번 스펙 범위에서 뺀 것들, 왜 뺐는지 포함:

- **Cloudinary로 전환** — 이 프로젝트에서 Cloudinary는 런타임 사용자 업로드
  (커뮤니티 게시물·노트 사진) 전용으로 설계돼 있다. 운영자가 큐레이션하는 정적
  콘텐츠엔 안 맞고, 원본 유실 문제 자체를 해결해주지도 않는다.
- **Vercel Blob / Cloudflare R2 등 신규 객체 스토리지** — 지금 확정된 근시일
  규모(전시 3개, SIF급 914개 참가사, 방문객 5000명 가정)로 계산하면 저장
  ~270MB, 트래픽 월 20~30GB 수준이라 git 커밋 + Vercel 정적 호스팅으로 충분하다.
  새 벤더 계정·청구 표면을 늘릴 이유가 없다. (계산 근거는 "규모 검증" 절 참고.)
- **자체 서버(VPS)나 개인 PC를 서버로** — 가동시간·보안·TLS·백업을 전부 직접
  떠안게 되고, 개인 PC는 오히려 안정성이 지금보다 떨어진다(전원·네트워크 단절 시
  전체 이미지 다운). 이 문제의 해법이 아니다.
- **전시 100개~5000개 규모의 플랫폼 전체 이미지 아키텍처** — 사용자가 장기
  비전으로 언급했으나, 근시일 확정 수치(3개 전시)와는 자릿수가 다른 별개의 큰
  프로젝트다. 실제로 그 규모가 임박하면(트래픽이 지금 계산의 10~100배가 되는
  시점) 그때 R2 같은 무료-egress 스토리지로 다시 설계한다. 지금 미리 옮기지
  않는다.
- **webp → jpg/png 전환** — 실측 비교(A안 참고) 결과 동일 품질에서 webp가 jpg보다
  56% 작고 png보다 12배 작다. 브라우저 호환성도 Safari 14(2020)부터 문제없다.
  바꿀 이유가 없다.

## 규모 검증 (근시일 확정 수치)

- 전시 3개 × SIF급 914개 참가사 × 부스당 ~100KB(원본 ~80KB + 파생 webp ~22KB,
  하우스 아카이브 실측 기준) ≈ **저장 270MB**.
- 방문객 5000명 × 세션당 이미지 100장(넉넉한 추정) × 파생 webp 22KB ≈
  **월 트래픽 11GB**(넉넉히 잡아도 20~30GB).
- `public/`에 git으로 커밋된 정적 파일은 Vercel이 이미 내고 있는 호스팅 요금의
  대역폭에 포함되어 서빙된다 — 별도 청구 항목이 생기지 않는다.
- 위 규모에서 git 커밋 방식은 저장·트래픽 모두 무리 없이 감당된다.

## 설계 — 공개/비공개 분리

핵심 결정: **사이트에 노출되는 파생 이미지와, 복구용으로만 필요한 원본을 서로
다른 곳에 둔다.**

| | 파생 webp (공개) | 원본 스크린샷 (비공개) |
|---|---|---|
| 내용 | 트림·크롭된 480px 썸네일 | 인스타그램 게시물 원본 스크린샷 |
| 저장 위치 | `public/booths/{전시}/{코드}.webp`, **public git 레포에 커밋** | Supabase의 **새 private 버킷**(예: `booth-originals`) |
| 이유 | 이미 사이트에 공개되는 콘텐츠라 레포 공개로 새로 노출되는 게 없다. Vercel 정적 호스팅이 대역폭을 이미 포함. | 제3자 소유 콘텐츠라 public 레포에 올리면 무단 재배포가 된다. 로컬 폴더 유실과 무관하게 복구 가능해야 한다. |
| 접근 빈도 | 높음(방문객 전체) | 낮음(운영자·재생성 스크립트만) |

### 데이터 흐름

1. 운영자가 CSV + 원본 스크린샷을 로컬 `public/house_archive_br/`에 둔다
   (지금과 동일, 변경 없음).
2. `node scripts/gen-house-archive-enrichment.mjs` 실행:
   a. 지금 하던 대로 JSON(`enrichment-house-archive-2026.json`) 갱신.
   b. 지금 하던 대로 `public/booths/house-archive/{코드}.webp` 생성(git 커밋 대상,
      변경 없음).
   c. **(신규)** 이번 실행에서 실제로 매칭·사용된 원본 파일들을 Supabase private
      버킷에 `house-archive-2026/{코드}.jpg`로 업로드(upsert — 같은 코드 재업로드
      시 덮어쓰기). 전시 slug로 경로를 나누는 이유: 버킷을 다른 전시와 공유해도
      코드가 겹치지 않게(예: 다른 전시에도 `H01`이 있을 수 있음).
3. 로컬 `house_archive_br/` 폴더가 사라지거나 오염돼도, 버킷에서 원본을 다시
   받아 재크롭할 수 있다.

### 구현 범위

- **수정**: `scripts/gen-house-archive-enrichment.mjs`만 손댄다. 기존 크롭·JSON
  생성 로직(라인 133-169)은 그대로 두고, 이미지 루프 마지막에 업로드 스텝을
  추가한다. `@supabase/supabase-js`(이미 프로젝트 의존성)와 `.env`의
  `SUPABASE_SERVICE_ROLE_KEY`를 그대로 재사용 — 새 패키지·새 자격증명 없음.
- **수동 1회**: Supabase 대시보드에서 private 버킷 생성(`booth-originals`).
- 다른 스크립트·컴포넌트·API 라우트는 건드리지 않는다.

### 에러 처리

- 버킷 업로드는 durability를 위한 부가 기능이다 — 실패해도 크롭·JSON 생성(스크립트의
  핵심 산출물)을 막지 않는다. 업로드 실패 시 파일명과 에러를 콘솔에 경고로
  출력하고 다음 파일로 진행한다(스크립트 전체를 죽이지 않음).
- 업로드는 upsert이므로 재실행 안전(멱등) — 기존 스크립트의 멱등성 원칙과 동일.

### 테스트

- `gen-house-archive-enrichment.mjs`는 지금도 자동 테스트가 없는 데이터
  파이프라인 스크립트다(리포지토리 컨벤션과 일치 — 운영자가 직접 실행하고 결과
  개수를 콘솔 로그로 확인하는 방식). 업로드 스텝 추가 후에도 동일한 방식을
  따른다: 실행 후 "업로드 성공/실패 카운트"를 로그로 출력해 눈으로 확인한다.
  이 스크립트 규모에 자동 테스트 인프라를 새로 얹는 건 과하다.

## 후속 (이번 스펙 범위 밖, 기록만)

- 전시 수·트래픽이 실제로 이번 계산의 10~100배 규모에 근접하면, 파생 웹 이미지
  서빙 자체를 R2 등 무료-egress 스토리지로 옮기는 재설계가 필요하다. 그때 실제
  숫자로 다시 판단한다.
- 100개 이상 전시를 운영자가 코드 변경 없이 온보딩하는 워크플로(지금은 CSV+스크립트
  +PR 방식)도 그 시점에 별도로 설계해야 한다.
