# R4 — 온디맨드 grounding ("왜 이거?"의 순간에만)

**날짜**: 2026-08-12
**성격**: 설계 문서 — 미착수(로미 개선 브리프 §3 R4).
**관련 파일**: `src/components/companion/companion-bar.tsx`(현재 `a3` 캔 답변), `src/components/booth/booth-personal-panel.tsx`(부스 상세 트리거 후보), `src/lib/ai/gemini.ts`(`generateGrounded`), `src/lib/loading-messages.ts`, `src/lib/feed/grounding.ts`(`Grounding` 타입 — 캐시 스키마 참고)

## 배경 — 현재 "왜 이거?"는 부스 무관이다

브리프는 "현재 캔 답변 a3"를 R4의 트리거로 지목하는데, 조사해보니 **a3는 특정 부스와 무관한 전역 FAQ**다:

- `companion-bar.tsx`의 `CompanionChat`은 `companion.q1/a1`, `q2/a2`, `q3/a3` 세 쌍을 하드코딩해 보여주는 탭이다. 어떤 화면에서 열어도 항상 같은 세 문답이고, boothId를 받지 않는다.
- `a3` 텍스트: "네 관심 가치랑 겹치는 부스라 골랐어. 카드의 색 태그가 그 연결 고리야" — 이것도 특정 부스를 가리키지 않는 일반 설명이다.

**결론: R4의 실시간 grounding을 걸 "그 부스"가 없다.** a3를 실시간 답변으로 바꾸는 게 아니라, **부스가 실제로 정해지는 자리에 새 트리거를 만들어야** RAG를 걸 대상이 생긴다.

## 목적

전 부스 사전 저작(R1) 대신, 사용자가 실제로 "이 부스, 왜 추천했어?"를 물은 **그 부스 하나만** 그 순간 `generateGrounded`로 실시간 보강하고 결과를 캐시해 재사용한다.

## 설계 — 트리거 위치 (옵션 비교)

- **A. 부스 상세(`BoothPersonalPanel`)에 새 버튼** — "로미한테 물어보기" 같은 명시적 액션. boothId가 이미 props로 있어 배선이 가장 짧다. 하지만 부스 상세는 "내 판단·메모" 자리라 컨셉이 약간 다르다(개인 기록 vs 정보 탐색).
- **B. 피드 카드(`interest-feed.tsx`)의 근거 절 옆에 "더 알아보기"** — 이미 `grounding.ts`가 만든 근거(사실/왜맞음)가 저작 데이터 없을 때 부스명 폴백까지만 가는 자리라, 정확히 R4가 채우려는 공백과 맞닿아 있다. 카드 단위라 boothId도 있다.
- **권장: B, 단 A도 같이(점진 확장).** 피드 카드는 "저작 데이터가 부실해서 근거가 얕다"는 문제가 실제로 드러나는 자리라 R4의 가치가 가장 크게 느껴진다. 부스 상세는 이미 공식 정보(요약·인스타 등)가 있어 온디맨드 grounding의 한계효용이 더 작다 — 그래도 "더 알아보기"를 부스 상세에도 노출하는 건 A의 컴포넌트만 재사용하면 되는 낮은 추가 비용이라 같이 갈 수 있다.

## 설계 — 흐름

```
사용자가 카드/부스 상세에서 "로미한테 물어보기" 탭
  → 캐시 확인(아래) — 있으면 즉시 표시(LLM 호출 없음)
  → 없으면 로딩 UX(loading-messages.ts에 새 토픽 추가, 아래) + generateGrounded 1회 호출
  → 결과를 캐시에 저장 + 화면에 표시
  → 실패 시 결정론 폴백: 기존 grounding.ts의 fact 사다리 결과(이미 있음)를 그대로 보여준다
    (완전히 새로운 실패 텍스트를 만들 필요 없음 — 이미 "빈말 대신 가진 사실" 폴백이 있다)
```

## 설계 — 캐시

**캐시 안 하면 같은 부스를 두 번째 사람이 물어볼 때마다 또 호출한다 — 첫 번째 사람이 낸 답이 사실상 R1의 초안과 동급이니 재사용해야 한다.**

- 캐시 키: `boothId`(부스 단위 — 사용자 단위 아님. "이 부스가 왜 좋은지"는 사용자 취향과 무관한 사실 정보라 공유 가능).
- 캐시 형태: `booth_enrichment`의 저작 필드와 **같은 스키마**에 저장(`roamInterpretation` 등) — "저작 필드처럼 재사용"이라는 브리프 문구 그대로. 즉, R4가 만든 답이 사실상 R1의 초안 하나를 실시간으로 만드는 셈 — **R4와 R1은 같은 목적지(저작 필드)에 도달하는 두 가지 다른 트리거(배치 vs 온디맨드)일 뿐**이다. 이 관계를 명시해두면 나중에 "R4로 채워진 필드를 R1 배치가 또 덮어쓰면 안 된다"는 규칙도 자연스럽게 따라온다(house-archive 규약 — 저작 필드는 재생성 시 보존).
- 무효화: 없음(이번 범위). 부스 정보가 바뀌는 빈도가 낮고, 운영자가 필요하면 수동으로 필드를 지우면 다음 요청이 다시 채운다.

## 설계 — 로딩 UX

`loading-messages.ts`에 새 토픽 `grounding` 추가:
```ts
grounding: [
  "이 부스 정보를 더 찾아보는 중이야",
  "웹에서 관련 소식을 확인하는 중이야",
],
```
주의: 기존 `route` 토픽 주석이 "동선 추천"을 언급하는데 동선 제품은 이미 제거됐다(CLAUDE.md) — `route` 토픽 자체가 지금 실제로 어디서 쓰이는지(피드 재추천 등으로 이름만 남았는지) 이번 작업 시작 시 먼저 확인 필요. 죽은 참조라면 `route`를 `grounding` 용도로 이름만 바꿔 재사용하는 것도 방법.

## 수용 기준

- "로미한테 물어보기" 탭 → 1초 이내 로딩 UX 표시(빈 화면 없음, 기존 규칙).
- 같은 부스를 두 번째로 물으면 LLM 재호출 없이 즉시 표시(캐시 히트).
- 실패해도 화면이 깨지지 않는다(기존 fact 사다리로 폴백).
- 피드 렌더·컴패니언 탭(즉답)에는 이 경로가 전혀 안 걸린다 — speed rule 검증은 "명시적 버튼 탭 이후에만 네트워크 호출이 나가는지" 수동 확인.

## 리스크 / 미해결

- 캐시를 `booth_enrichment`에 바로 쓰면 "사람 승인 없이 자동으로 저작 필드가 채워진다"는 뜻이다 — R1은 "초안 → 사람 승인" 흐름인데 R4는 승인 없이 즉시 반영된다. 품질 기준이 다르다는 뜻이라, 별도 컬럼(`roamInterpretationAuto` 등)에 넣고 화면엔 "AI가 방금 찾아본 내용" 같은 출처 표시를 다는 게 더 정직할 수 있다 — 이번 문서에서 확정하지 않음, 구현 착수 시 결정.
- R1(배치)과 R4(온디맨드)가 같은 필드를 다른 시점에 채우면 경쟁 조건(동시에 둘 다 같은 부스를 채우려는 경우)이 이론상 가능 — 실사용 빈도가 낮아 이번 범위에선 무시 가능하지만 기록만 남긴다.
