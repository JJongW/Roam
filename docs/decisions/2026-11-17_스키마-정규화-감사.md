# 스키마 정규화 감사, 브랜드가 뿌리이고 부스는 나중

_2026-11-17. 요청: Ted("supabase에 지금 부분종속으로 엮인 건 없는지 확인하고 어느 정도 정규화를 해놔야 할 것 같은데. 지금 부스 번호가 있는 건 필수가 아니라고 분명히 말했는데 왜 계속 필수인 것처럼 잡혀 있지?"). 분석과 마이그레이션 초안만이다. **운영에 적용한 것은 없다.**_

초안: `supabase/migrations/_draft/participant-rekey.draft.sql`(번호 없음, 적용 안 함).

## 결정 (Ted, 2026-11-17)

> 무조건 브랜드가 우선이라고. 브랜드가 어떤 박람회에 참여하던 말던은 자유겠지. 근데 특정 브랜드가 어떤 박람회에 참여한대, 그럼 그때 '오 하는구나' 하고 등록하면 그만인 거라고. 부스는 그 이후인 거지.

이 문장이 목표 모델을 고정한다. 여러 안 중 하나가 아니다.

1. **브랜드(exhibitor)가 뿌리다.** 어느 박람회와도 무관하게 있다. 신원, 링크, 인스타, 프로필, 브랜드 단위 연락이 여기 붙는다.
2. **출전(exhibition_participant, 브랜드 × 박람회)은 가벼운 기록이다.** 참가 소식을 알게 된 때 만든다. 부스가 필요 없다.
3. **부스 배정(booth_participant, 출전 × 부스)은 그 다음이고, 선택이고, 바뀔 수 있다.** 자리에 속한 것(좌표, 하트, 메모, 다녀왔어요)만 부스에 남는다.

## 2. 정규화 위반

### 2-1. 부분 종속(2NF), 그리고 "브랜드 사실을 부스에 둔 것"

엄밀한 복합 키 테이블(`booth_note`, `booth_participant`, `survey_response`, `exhibition_participant`의 unique 쌍)은
속성이 키 전체에 기대고 있어 2NF 위반이 없다. 문제는 키를 잘못 고른 테이블이다.

| # | 테이블.칸 | 마이그레이션 | 무엇에 기대는가 | 지금 무엇이 깨지나 |
|---|---|---|---|---|
| P1 | `brand_contact` 전체(PK booth_id) | 0061 | 연락 상태와 허락 범위는 **브랜드 × 회차**(출전)에 기댄다. 부스는 그 회차의 자리일 뿐이다. `handle`, `channel`은 브랜드에만 기댄다 | 부스 없는 출전 251곳(newyear-store)에 연락 행을 못 만든다. 0061 주석 스스로 "한 행 = 그 브랜드의 그 박람회 회차"라고 적고 부스를 대리 키로 썼다. 원본인 Roam-design `permissions.csv`에는 부스 칸이 아예 없다(팀 이름이 열쇠). 부스가 지워지면(번호를 바꿔 다시 인입) **연락과 VOC가 cascade로 같이 지워진다**. 공동 부스면 브랜드 둘이 연락 행 하나를 나눠 쓴다 |
| P2 | `exhibitor_link_candidate.booth_id` not null | 0057 | "같은 브랜드인가"는 출전(그 회차의 그 브랜드)에 대한 판단이다 | 부스 없는 출전은 후보가 될 수 없다. 11-10 결정 기록이 이걸 "버린 방법"에 적고 미리보기 목록으로 우회했다 |
| P3 | `booth.instagram_url`, `website_url`, `logo_url`, `images`, `company`, `name` | 0001, 0002 | 인스타, 웹, 로고, 브랜드 사진은 브랜드에 기댄다. `name`은 출전 표기(회차별) | 같은 사실이 `exhibitor.instagram_url`, `brand_profile_field`(links, photos), 부스 세 곳에 있다. 운영에서 23곳이 서로 다르고 113곳은 부스에만 있다. 신원 판정(`exhibitor/service.ts`)은 부스 값을 합쳐 쓰고 `exhibitor.instagram_url`은 만든 뒤 고치는 경로가 없어 낡는다 |
| P4 | `booth_enrichment.summary`, `roam_interpretation`, `memory_hooks` | 0013, 0021 | 브랜드에 기댄다(그래서 이월 `carryover.ts`가 지난 부스에서 복사한다). `timing`, `things_to_do`는 회차에 기댄다 | 한 테이블에 두 수준이 섞여, 이월 때 칸별로 "넘겨도 되는가"를 코드가 기억해야 한다. 공식 소개는 0061 뒤로 `brand_profile_field.intro`가 원천이 되어 소개가 세 곳(부스 원문, enrichment.summary, intro)에 있다(우선순위는 `2026-11-03_브랜드-프로필-0061-적용-절차.md` 2절) |
| P5 | `booth.aliases`(공동 입점 이름 jsonb) | 0007 | 공동 출전은 `booth_participant.role = co_exhibitor`가 맡는 사실 | 같은 사실의 두 모델. 운영 co_exhibitor 0행, 공동 입점은 aliases에만 있다 |

## 3. 부스가 필수가 아닌데 필수로 잡힌 곳

모델(결정): 브랜드가 있고, 박람회에 **출전**하고(exhibition_participant), 자리는 나중에 **배정**된다(booth_participant).
0040이 이미 이 모양이다. 부스가 필수로 잡힌 곳은 그 아래 단계다.

| 자리 | 부스를 요구하는 방식 | 부스 없는 출전에서 생기는 일 | 어디로 옮기나 |
|---|---|---|---|
| 연락 `brand_contact`, `brand_contact_log` | PK와 FK가 booth_id(0061). API `/api/admin/brands/contacts/[boothId]`, 저장소 `getBrandContact(boothId)` 등 | 연락 행을 못 만든다. 브랜드 상세 "연락" 탭이 출전 목록을 부스에서 만들어 탭이 비어 있다. 박람회가 없는 브랜드(문구전 작가 7팀, `exhibitionSlug: null`)는 어디에도 못 붙는다 | **나눈다.** 연락처와 VOC는 브랜드로, 허락은 출전으로(5-2) |
| 브랜드 목록 `lib/brands/directory.ts` | 출전(`appearances`)을 부스에서만 만든다 | 251곳이 "출전 없음". 박람회로 거르면(`filterDirectory`) 아예 사라진다 | 코드만. 출전에서 만들고 부스는 붙으면 붙인다 |

### 5-2. 연락과 허락은 어디에 붙나 — 나눈다

| 묻는 것 | 어디에 기대나 | 자리 | 이유 |
|---|---|---|---|
| 이 브랜드에 누구로 어떻게 닿나(채널, 핸들) | 브랜드 | `brand_outreach` | 박람회가 바뀌어도 같은 계정이다. 회차마다 두면 박람회 수만큼 사본이 생기고 어긋난다(P1과 같은 병) |
| 더 연락하지 말아 달라(내려 달라는 요청 등) | 브랜드 | `brand_outreach.do_not_contact` | 한 회차에서 받은 요청이라도 다음 박람회에 또 DM을 보내면 안 된다 |
| 오간 말(VOC) | 브랜드, 선택으로 회차 | `brand_outreach_log`(exhibitor_id 필수, participant_id 선택) | 대화 상대는 브랜드다. 박람회가 아직 없는 브랜드(문구전 작가 7팀)와도 대화가 있었다 |
| 이번 회차 콘텐츠에 무엇을 써도 되나(상태, allowed_use, 받은 사진과 글, 체크리스트) | 출전 | `participant_permission`(PK participant_id) | 카드뉴스 허락은 쓰임마다 받는다. 지금 운영 단위인 `permissions.csv`가 박람회 회차 폴더(`runs/moongu-2026-winter/`)마다 있고, 0061도 "같은 브랜드도 박람회마다 따로 묻고 허락 범위도 다를 수 있다"고 적었다. 부스는 필요 없다 |

- 회차보다 더 잘게(카드뉴스 한 편마다) 허락을 받게 되면 `participant_permission` 아래에 쓰임 행을 더한다. 지금은 회차당 한 행으로 충분하다(csv와 같은 단위).
- 허락에 박람회가 없는 경우(박람회 미정 브랜드의 사진을 쓰고 싶을 때)는 결정 2대로 "참가 소식을 알게 된 때" 출전을 만들고 거기에 허락을 단다. 박람회와 무관한 쓰임(브랜드 소개 글)은 지금 사례가 없어 만들지 않는다.
- FK: 브랜드 쪽은 `on delete restrict`다. 브랜드 합치기(`mergeExhibitor`)가 브랜드를 지우기 전에 연락처와 VOC를 옮기게 강제한다(칸 옮기기와 같은 규칙: 겹치면 대상 것을 지키고, VOC는 전부 대상으로). 출전 쪽 허락도 restrict이고, 같은 박람회 출전 둘이 합쳐질 때 같은 규칙으로 옮긴다. 허락의 박람회 일치는 트리거 대신 복합 FK `(participant_id, exhibition_id) → exhibition_participant(id, exhibition_id)`로 지킨다.

## 6. 인입 변경 — 브랜드 먼저, 번호는 나중

### 6-1. 규칙

- `/admin/intake` 하나로 받는다(레포 규칙). 
- **intake.v1 행의 `code`를 선택으로 바꾼다.** code가 없는 행은 부스를 만들지 않고 브랜드와 출전만 만든다. 처리는 brands.v1 계획(`brands-plan.ts`)을 그대로 탄다 — 파싱 때 code 없는 행을 brands.v1 브랜드 모양으로 바꿔 넘기므로 판정 코드가 두 벌이 되지 않는다.
- 행에 `brandKey`를 새로 받는다. code 없는 행은 `brandKey`가 필수(나중에 번호를 붙일 열쇠), code 있는 행은 선택.
- brands.v1 파일은 그대로 받는다. 박람회가 없는 브랜드(`exhibitionSlug: null`)는 이 파일로만 넣는다.
- 11-10 결정 기록은 "intake.v1에 부스 코드 없는 행을 허용"을 버렸다. 버린 이유는 "code 없는 부스는 지도에 못 뜨는 가짜 부스가 된다"와 "계획의 모든 판정이 code를 자연키로 쓴다"였다. 이번 안은 code 없는 행을 **부스로 만들지 않고**, 부스 계획에 넣지 않으므로 두 이유에 걸리지 않는다. 2026-11-17 결정이 이 경로를 요구한다.

### 6-2. 번호가 나왔을 때(같은 파일, 같은 경로)

부스 행에 `code` + `brandKey`:

1. 같은 박람회에 `intake_key = brandKey`인 출전이 있으면 그 출전에 **정확히** 잇는다(이름 맞추기 건너뜀).
   - 그 출전에 대표 부스가 **없으면** → 이 code로 부스를 만들고 배정한다.
   - 대표 부스가 **있고 code가 다르면** → 새 부스를 만들지 않고 **그 부스의 code와 좌표를 고친다**. 미리보기에 "번호 바뀜 NY303 → B-12"로 보인다. 부스 id가 그대로라 하트, 메모, 다녀왔어요가 살아남는다(결정 3 "바뀔 수 있다").
   - code가 같으면 → 지금처럼 빈 칸만 채운다.
2. 출전이 없으면 → 브랜드 먼저 규칙으로 브랜드와 출전을 만들고(또는 인스타와 도메인으로 기존 브랜드를 찾고) 부스를 배정한다.
3. `brandKey`가 없으면 → 지금 순서(인스타와 도메인, 같은 박람회 이름 일치, 새 브랜드).
4. 번호를 서로 맞바꾸는 경우(A1 ↔ A2)는 unique(exhibition_id, code)에 걸린다. 적용을 두 번에 나눈다(임시 code로 비켜 두고 고침).
5. 자리를 옮기는 경우(출전 X의 부스가 다른 칸으로)도 같은 경로다. 배정이 바뀌는 것이고 브랜드와 출전은 그대로다.

### 6-3. 새해 준비상점에 적용하면

brands.v1은 이미 적용됐다(출전 251). STEP 2가 `intake_key`를 `ny-303` 등으로 채운다. 번호와 도면이 나오면
`data/intake/_review/newyear-store-2026.json`의 `NY303`을 실제 번호로 바꾸고 각 행에 `brandKey: "ny-303"`을 붙여 올린다(열쇠는 이미 주최 측 브랜드 번호로 맞다).
도면이 없는데 임시 번호로 부스를 먼저 올리지 않는다는 11-09 판단은 그대로다(도면에 없는 code는 0,0).

## 7. 마이그레이션 단계

적용은 손으로(SQL Editor), 단계마다 main 기준 다음 번호(0062부터)로 옮겨 적는다. 초안은 PGlite(Postgres 16, 0001~0061을 순서대로 적용한 뒤)에서
STEP 0~4와 STEP 1~3 되돌리기를 돌려 확인했다: 부스 없는 출전에 허락 쓰기, 박람회 없는 브랜드에 연락처 쓰기, 박람회 어긋남 차단, 브랜드 삭제 차단(restrict),

## 7-1. STEP 1, 2를 번호 파일로 (2026-11-17, Ted 승인)

- **백업**: `data/intake/_backup/schema-step1-before-2026-11-17T03-26-26-011Z.json`(exhibitor 2513, exhibition_participant 2595, booth_participant 2391, exhibitor_link_candidate 33, booth 2430, brand_contact 0, brand_contact_log 0).
- **사전 확인**(백업 기준): 대표 배정 없는 후보 0, brandKey 중복 0, (exhibition_id, code) 중복 0. 0063 기대값: intake_key 251, 후보 participant_id 33, 브랜드 인스타 112곳과 웹 105곳 채움, 새 테이블 0행.
- PGlite에서 0001~0061 뒤 0062, 0063을 두 번씩 돌려 멱등을 확인했고, 옮기기 함수로 합치기를 흉내 내 restrict가 옮기지 않은 삭제를 막는 것, 옮긴 뒤엔 지워지는 것을 확인했다.

### FK를 restrict로 둔 이유와 합치기

합치기와 삭제 경로를 찾았다(`src/lib/supabase/repository.ts` `mergeExhibitor`). 출전이나 브랜드를 지우는 곳은 여기 둘뿐이다.
- 같은 박람회에 대상 브랜드의 출전이 이미 있으면 from 출전을 **지운다**(`exhibition_participant` delete).
- 끝에 from 브랜드를 **지운다**(`exhibitor` delete).
- `applyExhibitorPlan`은 넣기만 하고, 박람회를 지우는 경로는 없다.

| 고를 수 있던 것 | 결과 | 판단 |
|---|---|---|
| cascade | 합치는 순간 연락 금지, 허락, VOC가 소리 없이 사라진다 | 버림. 감사의 의도(연락과 허락을 잃지 않는다)와 정반대 |
| set null | 주인 없는 연락처와 허락이 남는다. 허락은 PK라 null이 안 된다 | 버림 |
| **restrict + 합칠 때 옮기기** | 옮기지 않은 합치기는 실패로 드러나고, 옮기면 남는다 | 고름 |

- 옮기기는 0062의 SQL 함수 둘이다(칸 옮기기 `move_brand_profile_fields`와 같은 방식). `move_participant_permission(from, to)`를 from 출전을 지우기 전에, `move_brand_outreach(from, to)`를 from 브랜드를 지우기 전에 부른다.
- 겹칠 때의 규칙: 연락처는 대상 것을 지키되 빈 칸을 채우고, 연락 금지는 하나라도 켜져 있으면 켠다. 허락은 대상이 아직 not-sent면 from 것으로 바꾸고, 진행된 허락이 있으면 대상 것을 지킨다. VOC는 전부 대상으로 옮긴다.
- VOC의 participant_id만 set null이다. 출전이 사라져도 기록은 브랜드 VOC로 남아야 한다.
- 연결 후보의 participant_id는 cascade다. 판단 대기라 0057의 부스 쪽과 같다.
- ⚠️ **`mergeExhibitor`가 아직 두 함수를 부르지 않는다.** 새 테이블이 0행인 동안은 문제가 없다. 연락 보드(`feat/admin-contact-board`)가 새 테이블에 쓰기 시작하면, 그 전에 합치기가 두 함수를 불러야 한다. 안 부르면 연락이 있는 브랜드의 합치기가 중간에 실패한다(부스 배정과 칸은 이미 옮겨진 상태로).

## 버린 방법

- **고르기 안으로 두기(brands.v1만, intake.v1 code 필수 유지)**: 처음 초안의 추천이었다. 2026-11-17 결정이 "브랜드 먼저 등록, 부스는 그 이후"를 같은 인입에서 하라고 해서 code 선택으로 바꿨다. 단점이던 "판정 두 벌"은 code 없는 행을 brands.v1 계획으로 넘겨 피한다.
- **연락 전부를 출전에**: 처음 초안의 안이었다. 핸들과 연락 금지가 회차마다 사본이 되고, 박람회 없는 브랜드와의 대화를 둘 곳이 없다.
- **연락 전부를 브랜드에**: 허락이 회차와 쓰임마다 다르다는 0061 결정, 회차별 `permissions.csv` 운영과 어긋난다.
- **출전에 `booth_id` 칸을 더해 nullable로**: 공동 부스와 대표 배정 규칙(0040 unique 인덱스)을 다시 만들어야 하고, booth_participant와 같은 사실이 두 곳에 생긴다.
- **옛 `brand_contact`의 키만 바꾸기**: 이름이 같은데 뜻이 바뀌어, 지금 그 테이블에 기대는 브랜치와 옛 코드가 틀린 값을 조용히 쓴다. 0행이라 새 테이블이 더 싸다.
- **허락에서 exhibition_id 칸을 아예 빼기**: 3NF로는 맞지만 박람회별 진행 현황 인덱스를 쓰려면 조인이 필요하다. 칸을 두고 복합 FK로 어긋날 수 없게 묶었다.
- **임시 번호(NY303)로 부스를 먼저 올리기**: 0,0 가짜 부스가 지도에 뜨고, 번호가 바뀌면 새 부스가 생긴다(11-09 판단 그대로). 6-2가 생긴 뒤에도 도면 없는 부스는 올리지 않는다.
